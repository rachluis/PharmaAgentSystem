# 第3章 系统需求分析与设计

本章依据软件工程的设计规范，对医药市场画像与策略生成系统进行详细的需求分析与系统设计。首先明确了系统的功能角色与业务需求，进而设计了“Web 后端 + 算法引擎 + AI Agent”的总体架构，详细定义了数据库模型与 E-R 关系，并对核心的智能体工作流与数据流转过程进行了逻辑编排。

## 3.1 需求分析

### 3.1.1 用户角色

本系统主要面向医药企业的市场部人员，具体划分为以下两类用户角色：

1. **系统管理员 (Admin)**：负责用户账号管理、系统日志审计及基础参数配置，拥有系统最高权限。
2. **数据分析师 (Analyst)**：系统的核心使用者，负责上传更新数据、执行聚类分析任务、查看可视化报表以及触发 AI 策略生成。

### 3.1.2 功能需求

根据业务流程，系统需具备以下核心功能模块：

1. **数据管理模块**：支持 CSV 格式医生交易数据的批量导入、清洗与结构化存储。
2. **画像分析模块**：
    * 支持自定义 RFM 权重与 K 值参数（2-10）。
    * 调用后端 K-Means 算法执行聚类。
    * 提供 3D 散点图、雷达图等多维可视化展示。
3. **智能策略模块**：
    * 自动提取各聚类群体的统计特征（Cluster Centroids）。
    * 集成 LLM 智能体，支持流式生成（Stream Response）市场策略报告。
    * 支持报告的 Markdown 渲染、保存与导出。

### 3.1.3 非功能需求

1. **响应性能**：在 70 万数据量级下，聚类分析任务的端到端响应时间应控制在 60 秒以内；简单查询响应需小于 500ms。
2. **数据安全性**：鉴于部分医生 NPI 数据及支付信息的敏感性，系统需实施基本的用户认证（JWT Token）与访问控制。
3. **可扩展性**：算法模块应解耦设计，以便未来替换更先进的聚类算法（如 DBSCAN）或升级大模型接口。

## 3.2 系统架构设计

本系统采用经典的分层架构设计，自下而上分别为数据层、服务层与应用层，并引入外部 AI 服务作为增强。

### 3.2.1 总体架构图

系统整体遵循 B/S（Browser/Server）架构，逻辑结构如下：

1. **前端展示层 (Vue 3)**：负责 UI 交互、数据可视化渲染（ECharts）及与用户的实时反馈。
2. **后端服务层 (FastAPI)**：
    * **API 网关**：统一处理路由分发与鉴权。
    * **业务逻辑**：包含用户管理、任务调度等常规业务。
    * **分析引擎**：内置 Scikit-learn 算法库，负责执行数据预处理与机器学习任务。
3. **数据存储层 (SQLite)**：持久化存储医生画像、支付流水及分析结果。
4. **外部智能层 (Dify/LLM)**：作为独立的 Micro-service 存在，通过 REST API 与后端交互，负责处理复杂的自然语言生成任务。

### 3.2.2 核心数据流向

系统核心业务流转严格遵循“数据-信息-知识”的转化路径：

1. **数据 (Data)**：用户上传 CSV，经 ETL 清洗后存入 `doctors` 表。
2. **信息 (Information)**：用户触发分析，K-Means 算法将医生划分为不同 Cluster，生成结构化的 `cluster_results` 统计信息。
3. **知识 (Knowledge)**：后端将 Cluster 特征组装 Prompt 发送至 Dify，Dify 返回策略报告，完成从数字到决策建议的跃迁。

## 3.3 数据库设计

系统数据库设计遵循第三范式（3NF），核心包含医生画像、群组结果及策略报告三部分。为保持前后端命名规范一致，所有字段采用 Snake_case（下划线）命名。

### 3.3.1 实体-关系图 (E-R Diagram)

系统主要实体包括：User（用户）、Doctor（医生）、AnalysisTask（分析任务）、ClusterResult（聚类结果）与 AIReport（智能报告）。

* **Doctor** 与 **ClusterResult** 呈多对一关系（一名医生属于一个群组）。
* **ClusterResult** 与 **AIReport** 呈一对多关系（一个群组可生成多份不同视角的报告）。
* **User** 与 **AnalysisTask** 呈一对多关系。

### 3.3.2 核心数据表设计

依据项目文档 `DATA_DICTIONARY.md`，关键表结构设计如下：

1. **Doctors 表 (医生画像核心表)**
    * 用于存储医生的基础信息及计算后的 RFM 值。
    * 关键字段：
        * `npi` (PK, String): 医生唯一标识（10 位数字）。
        * `rfm_recency` (Int): 最近一次互动间隔天数。
        * `rfm_frequency` (Int): 年度互动频次。
        * `rfm_monetary` (Float): 年度累计金额。
        * `cluster_id` (FK, Int): 关联的聚类群组 ID。
        * `cluster_label` (String): 业务标签（如“核心高价值”）。

2. **ClusterResults 表 (聚类结果统计表)**
    * 用于存储每次分析后的群组统计特征，是 AI 生成策略的数据源。
    * 关键字段：
        * `cluster_id` (PK): 群组 ID。
        * `size_count` (Int): 该群组包含的医生数量。
        * `kpi_summary` (JSON): 存储 {"avg_monetary": 10462.26, "avg_frequency": 43.84} 等核心指标。
        * `strategy_focus` (String): 预设的策略重心简述。

3. **AIReports 表 (智能策略报告表)**
    * 存储 Dify 生成的 Markdown 格式报告。
    * 关键字段：
        * `report_content` (Text): 完整的策略报告内容。
        * `dify_conversation_id` (String): 关联的 Dify 会话 ID。
        * `related_cluster_id` (FK): 指向对应的分析群组。

## 3.4 Dify 智能体工作流设计

为了实现自动化的策略生成，在 Dify 平台编排了如下工作流：

### 3.4.1 输入层 (Input)

Agent 接收来自后端的 JSON 格式上下文，例如：

```json
{
  "cluster_name": "Cluster 0 (VIP)",
  "features": {
    "avg_monetary": 10462,
    "avg_frequency": 43,
    "top_specialty": "Cardiology"
  }
}
```

### 3.4.2 系统提示词 (System Prompt) 设计

设定了严格的生成指令：

* **Role**: 你是世界顶级的医药市场战略顾问。
* **Constraints**: 输出必须基于提供的 JSON 数据，严禁编造数据；必须遵守医疗合规准则。
* **Output Format**: 使用 Markdown 格式，包含 Title, Analysis, Strategy, Risk Scan 四个章节。

### 3.4.3 工作流逻辑

1. **数据解析节点**：将输入 JSON 解析为自然语言描述。
2. **推理节点 (LLM)**：结合医疗知识库，分析该群体的行为动机（如“高频互动说明对学术会议依赖度高”）。
3. **生成节点**：撰写具体的行动计划（如“建议邀请担任卫星会主席”）。

## 3.5 本章小结

本章完成了系统的详细设计，确立了以 FastAPI 为中枢、SQLite 为基石、Dify 为大脑的技术蓝图。特别是数据库设计中对 RFM 特征的结构化存储，以及 Dify 工作流中对数据到策略的映射逻辑，为下一章的具体代码实现提供了清晰的指导方案。
